# ICM Workspace: Blog Publishing Pipeline

**Purpose:** Takes a blog post from topic selection through publication-ready Jekyll markdown, using ICM's five-layer context hierarchy to deliver focused, stage-appropriate context at each step.

**Use:** Copy this file to a new project directory as `CLAUDE.md`. Run `stages/00_setup/` to configure reference material. Run Claude Code from the workspace root.

**Reference:** Van Clief & McDermott, "Interpretable Context Methodology: Folder Structure as Agent Architecture," arXiv:2603.16021v2, March 2026.

---

## Workspace Identity (Layer 0)

This workspace manages the full lifecycle of a blog post for startupctobook.com: selecting a topic, validating the angle before committing writing effort, researching, drafting, scoring against TTNW and the style guide, revising, and outputting Jekyll-ready markdown.

The pipeline is sequential with human review gates between stages. Each stage reads only the context it needs. No stage loads the full workspace. The folder structure is the orchestration — no framework, no coordination code.

The workspace follows ICM conventions:
- Numbered folders encode execution order
- Each stage has one job and writes output to its own `output/` folder
- `references/` folders hold stage-specific Layer 3 material; `_config/` holds shared Layer 3 material
- `output/` folders hold Layer 4 working artifacts that change every run
- Stage contracts (CONTEXT.md) specify exactly which files the agent loads — no guessing, no loading everything

### What changed from v1 and why

**The review loop is now two stages (05_score + 06_revise).** ICM is sequential — one stage, one job. The v1 "review loop" stage violated this by doing score + revise + re-score inside a single stage. The paper is explicit: "A stage that fetches data does not also filter it." Split the loop into separate stages. The human runs 05 → 06 → 05 → 06 until satisfied. Incremental recompilation: you re-run stages, you don't loop within one.

**Token budgets enforced.** The paper specifies ~500–2,000 tokens for Layer 3 per stage. The v1 design loaded the full style guide (3,000+ tokens) plus the TTNW rubric (2,000+ tokens) plus banned words into the same stage. Now: `voice.md` is a compressed extract (<500 tokens) used by the draft stage. The full `ttnw-rubric.md` is only loaded by stage 05 (scoring). `writing-rules.md` is only loaded by stage 04 (drafting) and stage 06 (revising). No stage loads everything from `_config/`.

**Stage 00 setup with questionnaire.** The paper's workspace-builder pattern includes a `setup/questionnaire.md` for first-time configuration. Added for voice calibration, audience definition, and Jekyll specifics.

**The `posts/` tracking folder is removed.** ICM's model is one pipeline run at a time. Stage output folders are the tracking mechanism. If you want to keep old runs, commit to git or copy the output folders manually.

**CorralData references removed, personal blog voice configured.** The voice is Gareth as CTO/author, not a company marketing department. Audience segments are CTOs, engineering leaders, and startup technical founders — not PE operators and practice managers.

**Each stage contract specifies exact files, not directories.** The paper calls this "the control point of the entire system." The v1 contracts were sometimes vague about which reference files load. Now every Inputs table lists specific files with specific purposes.

## Routing Table

| Task | Stages | Notes |
|------|--------|-------|
| New post from scratch | 01 → 02 → 03 → 04 → 05 → 06 → 05 → ... → 07 | Full pipeline. Loop 05↔06 until exit criteria. |
| Evaluate a topic only | 01 → 02 | Stop after pre-draft TTNW. Go/no-go decision. |
| Write from existing brief | 03 → 04 → 05 → 06 → ... → 07 | Skip selection. |
| Score an existing draft | 05 | Score only, no revision. |
| Revise a scored draft | 06 → 05 | Revise then re-score. |
| Re-draft (keep research) | 04 → 05 → 06 → ... → 07 | Re-run draft stage with same research. |
| Publish approved draft | 07 | Format and output only. |

The 05↔06 cycle is the review loop. It is not automated — the human runs stage 05, reads the scores, then decides whether to run stage 06 (revise) or proceed to stage 07 (publish). This is ICM's model: the human makes branching decisions between stages. Three cycles without reaching 11.0/14.0 → the human should consider whether the angle is wrong (back to 01) rather than continuing to polish.

### Incremental recompilation

ICM supports re-running individual stages without re-running the full pipeline. If the research is good but the draft doesn't work, re-run stage 04. If the voice guide changes in `_config/`, re-run only the stages that load it (04, 06). The stage contracts' Inputs tables are the dependency graph — a change to any listed file signals the stage output may be stale.

---

## Naming Conventions

- Topic slugs: lowercase, hyphenated (`metadata-quality-bottleneck`, `cto-ic-trap`)
- Draft versions: `-draft-v1.md`, `-draft-v2.md`
- Score files: `-score-v1.md`, matching the draft version scored
- Jekyll output: `YYYY-MM-DD-slug.md`
- Research: `-research.md` (single file per post)

# Stage Contracts

---

## Stage 00: Setup (one-time)

### Purpose
Configure the workspace's Layer 3 reference material by answering questions about voice, audience, and platform. Run once when the workspace is created. Run again if voice or platform changes.

### Inputs
- Layer 4 (working): `stages/00_setup/questionnaire.md`

### Process
Walk through the questionnaire. Answers generate or update the following `_config/` files:

**voice.md** — Based on:
- Who is the author? (Name, role, background)
- What's the voice in one sentence? (e.g., "A CTO who builds things, writes about what actually works, and has the scars to prove the claims")
- What would you never say? What would you always say?
- If someone read your last five posts, what adjectives would they use?
- Provide 2-3 paragraphs you've written that sound most like you

**writing-rules.md** — Based on:
- Target word count range for typical posts
- Opening rules (claim-first? scenario-first? question-first?)
- Closing rules (one-sentence crystallizer? CTA? open question?)
- Structure preferences (how do you use headers? numbered sections?)
- What annoys you most when you read other people's technical writing?

**banned-words.md** — Based on:
- Provide the existing kill list (or seed one from the style guide)
- What AI-generated phrases do you catch yourself deleting?
- What words does your industry overuse?

### Outputs
- `setup/answers.md` → completed questionnaire
- Updates to `_config/voice.md`, `_config/writing-rules.md`, `_config/banned-words.md`

## Stage 01: Op-Ed Selection

### Purpose
Evaluate a topic idea against the author's content strategy. Commit to a specific angle, audience, and thesis seed — or reject the topic with rationale.

### Inputs
- Layer 4 (working): User-provided topic idea (conversation or file)
- Layer 3 (reference): `stages/01_op_ed_selection/references/content-strategy.md`

### Process

**Relevance gate:**
- Does this connect to a problem the target reader actually has?
- Can the author say something other blogs cannot? (Production experience, real numbers, technical scars)
- Does it fill a gap in the content mix? (Check content-strategy.md for what's published and what's missing)

**Angle selection:**
- What is the specific tension? Not "building AI products is hard" but "metadata quality determines AI accuracy more than model selection, and here's a year of data"
- Who is the primary reader? One audience, named.
- What does the reader believe before reading that they should believe differently after?

**Differentiation check:**
- Is this a debugging story / postmortem? (Strongest format per the Luu research)
- Does it contain real numbers from production experience?
- Could this appear on any generic tech leadership blog? If yes, find the angle that couldn't.

**Output format — the brief:**
- Topic (one line)
- Angle (the specific tension or argument, 2-3 sentences)
- Thesis seed (one sentence the reader could disagree with, under 25 words)
- Primary audience (one named segment)
- Content type (debugging story / technical deep-dive / applied research / framework / opinion)
- Word count target
- Key points to cover (3-5)
- Differentiation statement (what makes this unsayable by someone who hasn't done the work)
- Co-author candidate (if applicable)

If the topic fails the relevance or differentiation gate: write a rejection with rationale and one suggested reframe.

### Outputs
- `[topic-slug]-brief.md` → `output/`

### Quality Checks (human review gate)
- Is the thesis seed specific enough to disagree with?
- Does the angle require knowledge only you have?
- Would you want to read this? If not, the angle is wrong.

## Stage 02: Pre-Draft TTNW

### Purpose
Score the brief against the TTNW tests evaluable before a draft exists. This is the kill gate. Below threshold → back to stage 01 for a new angle, not forward to drafting.

### Inputs
- Layer 4 (working): `../01_op_ed_selection/output/[topic-slug]-brief.md`
- Layer 3 (reference): `stages/02_pre_draft_ttnw/references/ttnw-pre-draft.md`

### Process
Score the brief against seven pre-draft-applicable tests:

| Test | Pre-draft question |
|------|-------------------|
| F1 Thesis Architecture | Is the thesis seed specific, falsifiable, and under 25 words? |
| F2 Mechanism/Interpretation | Does the brief separate what happened from what it means? |
| Fx1 Genre Awareness | Is the content type matched to the argument? |
| Fx3 Stands-Alone Self-Sufficiency | Will insider terms need definition for the named audience? Flag them. |
| O1 Reframe/Reconceptualization | Is there a novel framing or just conventional wisdom? |
| E2 Counterargument | What is the strongest objection? Is the brief prepared to engage it? |
| E4 Contextual Richness | Does the brief reference specific data, incidents, or precedents? |

Produce a scorecard: pass / flag / fail for each test, with specific revision notes for flagged items.

**Exit criteria:**
- All pass or flagged with clear revision path → proceed to 03
- Any fail → return to 01 with notes
- O1 fails (no novel framing) → kill or fundamentally reframe; do not proceed

### Outputs
- `[topic-slug]-ttnw-pre.md` → `output/`

### Quality Checks (human review gate)
- Do you agree with the pass/flag/fail calls?
- Go/no-go: research, re-angle, or kill?

---

## Stage 03: Research

### Purpose
Gather evidence, data, sources, and examples the draft will need. Structured raw material with attribution — not a draft, not analysis.

### Inputs
- Layer 4 (working): `../01_op_ed_selection/output/[topic-slug]-brief.md`
- Layer 4 (working): `../02_pre_draft_ttnw/output/[topic-slug]-ttnw-pre.md`
- Layer 3 (reference): `stages/03_research/references/source-standards.md`

### Process
For each key point in the brief:
1. Find supporting evidence (production data, published research, named companies)
2. Find counterevidence (what complicates or challenges the thesis)
3. Collect specific numbers, dates, names the draft can use
4. Note source quality tier:
   - Tier 1: Author's own production data (strongest)
   - Tier 2: Named companies, named researchers, published benchmarks
   - Tier 3: Industry reports, analyst estimates
   - Tier 4: General claims, unsourced assertions (minimize — each is a TTNW E1/E4 risk)

Structure output as:
- Claim → evidence → source → tier
- Counterarguments found → evidence → source
- Specific quotable data points
- Gaps: claims that couldn't be substantiated (flag for human)

Do not fabricate sources. If evidence doesn't exist, say so.

### Outputs
- `[topic-slug]-research.md` → `output/`

### Quality Checks (human review gate)
- Are sources real and verifiable?
- Enough Tier 1-2 to ground the piece?
- Did research surface a better angle? Note it.
- Are gaps acceptable or thesis-undermining?

## Stage 04: Draft

### Purpose
Write the first complete draft. Follows the brief's angle and thesis, incorporates research evidence, adheres to voice and writing rules.

### Inputs
- Layer 4 (working): `../01_op_ed_selection/output/[topic-slug]-brief.md`
- Layer 4 (working): `../02_pre_draft_ttnw/output/[topic-slug]-ttnw-pre.md` (for structural risks to address)
- Layer 4 (working): `../03_research/output/[topic-slug]-research.md`
- Layer 3 (reference): `_config/voice.md`
- Layer 3 (reference): `_config/writing-rules.md`
- Layer 3 (reference): `_config/banned-words.md`

**Token note:** This stage loads three Layer 3 files. voice.md must be under 500 tokens. writing-rules.md under 800 tokens. banned-words.md under 300 tokens. Total Layer 3: ~1,600 tokens, within the paper's 500–2,000 range.

### Process

**Structure** (from writing-rules.md):
- Open with a specific claim, tension, or scenario in the first two sentences. No warm-up.
- Thesis in the first paragraph. Stated, not hinted.
- Every H2/H3 works as a standalone outline entry.
- Close with one sentence that crystallizes. No restating the intro.
- Hit the word count target from the brief.

**Voice** (from voice.md):
- Write as the named author, not as a company or brand.
- Practitioner-credible: use the reader's vocabulary, name the tools, cite the numbers.
- Direct and declarative. Short sentences. Active voice.
- Opinionated. State what works and what doesn't. Don't hedge into mush.

**Evidence** (from research output):
- Ground every claim in something specific from research. Replace adjectives with data.
- Cite naturally — "Snowflake's benchmarks show 85%" not "According to a recent study..."
- When using your own production data, be specific.

**Anti-patterns** (from banned-words.md):
- Zero banned words in body copy.
- No "you can" / "you're able to" hedging.
- Every sentence must fail the generic test: could this appear on any tech leadership blog unchanged? If yes, rewrite until it couldn't.

### Outputs
- `[topic-slug]-draft-v1.md` → `output/`

### Quality Checks (human review gate)
- Read the first two sentences. Do they earn the third?
- Read aloud: smart colleague or press release?
- Visual needed? Note placement.

---

## Stage 05: Score

### Purpose
Score the current draft against the full TTNW 14-test rubric and check for style guide violations. Produce scores and specific flags. This stage does not revise — it only evaluates.

### Inputs
- Layer 4 (working): Latest draft (from `../04_draft/output/` on first run, or `../06_revise/output/` on subsequent runs)
- Layer 4 (working): `../01_op_ed_selection/output/[topic-slug]-brief.md` (for thesis alignment)
- Layer 3 (reference): `_config/ttnw-rubric.md`
- Layer 3 (reference): `_config/banned-words.md`

**Token note:** This stage loads ttnw-rubric.md (~1,500 tokens) and banned-words.md (~300 tokens). Total Layer 3: ~1,800 tokens.

### Process

**TTNW scoring** — all 14 tests, each scored 0.0–1.0 with rationale naming the specific passage or structural issue:

*Fluency (5 tests, max 5.0):*

| # | Test | Measures |
|---|------|---------|
| F1 | Thesis Architecture | Specific, falsifiable thesis in first paragraph. Under 25 words ideal. |
| F2 | Mechanism/Interpretation Separation | Separates what happened from what it means? |
| F3 | Sentence-Level Compression | Anything cuttable without information loss? Word count vs. content. |
| F4 | Evidence Integration | Sources woven into argument, not dumped. Every claim grounded. |
| F5 | Ending Integrity | One-sentence crystallizer. No restating. No wind-down. |

*Flexibility (3 tests, max 3.0):*

| # | Test | Measures |
|---|------|---------|
| Fx1 | Genre Awareness | Format matches argument type? |
| Fx2 | Register Fluidity | Tonal shifts signal transitions between technical/narrative/opinion? |
| Fx3 | Stands-Alone Self-Sufficiency | Every person, acronym, insider term introduced for named audience? |

*Originality (2 tests, max 2.0):*

| # | Test | Measures |
|---|------|---------|
| O1 | Reframe/Reconceptualization | Novel framing or conventional wisdom restated? |
| O2 | Structural Innovation | Structure serves the argument or default template? |

*Elaboration (4 tests, max 4.0):*

| # | Test | Measures |
|---|------|---------|
| E1 | Source Integrity | Claims sourced. No fabricated citations. |
| E2 | Counterargument | Strongest objection engaged, not strawmanned. |
| E3 | Analytical Depth | One level deeper than surface. Explains mechanisms, not just outcomes. |
| E4 | Contextual Richness | Specific data, precedents, named examples. Not assertions. |

Report:
- Individual scores with rationale
- Dimensional subtotals: Fluency X/5.0, Flexibility X/3.0, Originality X/2.0, Elaboration X/4.0
- **Total: X/14.0**
- Interpretation: 11.0–14.0 publication-grade / 9.0–10.9 strong draft / 7.0–8.9 structural issues / <7.0 kill or restart

**Style check:**
- Scan for every word on the banned list. Report line and replacement.
- Flag throat-clearing openers and hedging language.
- Flag any sentence passing the generic-blog test.
- Check all proper nouns and technical terms are introduced for the named audience.

**Verify** (cross-stage consistency, per ICM Section 6.2):
- Does the draft's thesis match the brief's thesis seed from stage 01?
- Does the draft use the evidence gathered in stage 03? Flag unused Tier 1-2 sources.
- Does the opening deliver on the angle promised in the brief?

**Known scoring biases:** AI tends generous on F3 (compression) and Fx2 (register fluidity). Human should calibrate these.

### Outputs
- `[topic-slug]-score-vN.md` → `output/`

### Quality Checks (human review gate)
- Agree with the TTNW scores? (Especially F3 and Fx2.)
- Agree with the style flags?
- Decision: proceed to stage 06 (revise), proceed to stage 07 (publish), or go back to stage 01 (wrong angle)?

## Stage 06: Revise

### Purpose
Revise the draft based on the scores from stage 05. One stage, one revision pass. The human then re-runs stage 05 to re-score.

### Inputs
- Layer 4 (working): Latest draft (from `../04_draft/output/` or own previous `output/`)
- Layer 4 (working): Latest score file from `../05_score/output/`
- Layer 3 (reference): `_config/voice.md`
- Layer 3 (reference): `_config/writing-rules.md`
- Layer 3 (reference): `_config/banned-words.md`

**Token note:** Same Layer 3 budget as stage 04 (~1,600 tokens). The score file is Layer 4 — it's this run's working material.

### Process

Revise the draft addressing the score file's findings. Priority order:
1. Any TTNW test below 0.7 (highest tier first)
2. All banned-word violations
3. All throat-clearing and hedging flags
4. Cross-stage consistency issues from the Verify section
5. Any remaining style flags

Do not over-revise. The goal is targeted fixes to the identified problems, not a full rewrite. If the score says F1 is 0.9 and E3 is 0.6, spend effort on E3 and leave F1 alone.

After revision, report what changed: which tests were targeted, what was cut/added/rewritten, expected impact on scores.

### Outputs
- `[topic-slug]-draft-vN+1.md` → `output/`

### Quality Checks (human review gate)
- Is the piece getting better or just getting different?
- Are you making the same edit you made last iteration? → **Edit-source signal.** Fix `_config/voice.md` or `_config/writing-rules.md`, not the draft. Recurring edits are debugging information: they point to Layer 3 problems.
- Ready to re-score (run stage 05 again)? Or ready to publish (skip to stage 07)?

---

## Stage 07: Publish

### Purpose
Convert the final draft into Jekyll-ready markdown with correct frontmatter. Output a file committable to the blog repo.

### Inputs
- Layer 4 (working): Final approved draft (from `../06_revise/output/` or `../04_draft/output/`)
- Layer 4 (working): `../01_op_ed_selection/output/[topic-slug]-brief.md` (for metadata)
- Layer 3 (reference): `stages/07_publish/references/jekyll-template.md`
- Layer 3 (reference): `_config/pre-publish-checklist.md`

### Process

**Frontmatter:**
```yaml
---
layout: post
title: "[from final draft H1]"
date: YYYY-MM-DD
author: "[from brief]"
categories: [from content-strategy mapping]
tags: [3-5 derived from content]
description: "[SEO meta, under 160 chars, primary keyword]"
image: /assets/images/blog/[slug]-hero.png
---
```

**Body:**
- Strip review comments, TTNW scores, revision notes
- Clean H2/H3 structure
- Convert internal links to blog URL format
- Add alt text placeholders for images
- Add closing CTA referencing this post's specific topic (not generic)

**Pre-publish checklist:**
- [ ] Intro: specific claim or tension in first two sentences?
- [ ] Zero banned words in body?
- [ ] Every claim grounded in metric, example, or scenario?
- [ ] Every H2/H3 works as standalone outline?
- [ ] Named author attribution?
- [ ] Visual noted (screenshot, diagram — not stock photo)?
- [ ] Closing CTA references post's specific topic?
- [ ] Under word count target?
- [ ] Read aloud: colleague or press release?
- [ ] Technical terms introduced for audience?
- [ ] SEO meta present, under 160 chars?
- [ ] Publication date set?

Report checklist results. Flag failures.

### Outputs
- `YYYY-MM-DD-[slug].md` → `output/`

### Quality Checks (human review gate)
- Frontmatter correct?
- First paragraph still good?
- CTA specific?
- Ready to commit to blog repo.

# Reference Material: What Goes in `_config/`

### voice.md (<500 tokens)
Compressed author voice. Not the full style guide — just the voice essence:
- Who the author is (one sentence)
- Voice in one sentence
- 5 ranked voice attributes (e.g., practitioner-credible, direct, opinionated, warm, technically fluent)
- What the author never sounds like (one sentence)
- 1-2 example paragraphs from published posts that nail the voice

This is the file the draft and revise stages load. It must stay under 500 tokens so it fits within the per-stage Layer 3 budget alongside writing-rules.md and banned-words.md.

### writing-rules.md (<800 tokens)
The mechanical rules. Sentence-level, paragraph-level, post-level:
- Opening rules (claim-first, no throat-clearing)
- Closing rules (one-sentence crystallizer)
- Header rules (each H2/H3 previews the argument)
- Evidence rules (adjectives → data, natural citation style)
- Length rules (default target, exceptions for research/framework pieces)
- The generic-blog test: if it could appear on any tech leadership blog unchanged, rewrite

### ttnw-rubric.md (~1,500 tokens)
Full 14-test rubric. Only loaded by stage 05 (scoring). Includes:
- All test definitions, tiers, and scoring criteria
- Dimensional groupings and maximums
- Aggregate interpretation bands
- Known AI scoring biases (generous on F3, Fx2)

### banned-words.md (<300 tokens)
The kill list, kept short. Loaded by stages 04, 05, and 06:
- unlock → name what becomes possible
- leverage / harness → use, apply, build on
- effortlessly / seamlessly → cut or describe what was hard
- empower → let, give [X] the ability to
- surface (verb) → find, show, flag
- supercharge → describe the specific improvement
- game-changer / breakthrough → describe what changed
- paradigm shift, next-generation, cutting-edge, best-in-class, synergy, holistic, robust, end-to-end (unless literal process), ecosystem (unless literal platform ecosystem)

Also flag: "This is not a theoretical concern," "The critical finding:," "with [adjective] precision," and any sentence starting with "It's worth noting that" or "Importantly,"

### pre-publish-checklist.md (<300 tokens)
The final gate. Only loaded by stage 07.

# The Edit-Source Principle

After each post is published, review the pipeline:

**Did you make the same kind of edit at the same stage across multiple posts?**

| Recurring edit | Fix in Layer 3 |
|---------------|----------------|
| Keep tightening the opening | Add a stronger opening rule to writing-rules.md |
| Tone drifts formal | Add a register example to voice.md |
| Misses counterarguments | Strengthen E2 description in ttnw-rubric.md |
| Generic tech-blog sentences survive to scoring | Sharpen the generic-blog test in writing-rules.md |
| Banned words sneak through | Audit banned-words.md — is the replacement guidance specific enough? |

Editing output fixes one post. Editing `_config/` fixes every future post. The workspace gets better with use only if the factory improves — not just the product.

# How to Use This Workspace

```
"I want to write about [topic]."
→ Run stage 01. Review brief. Run stage 02. Go/no-go.

"Brief is good, let's go."
→ Run 03 (research) → 04 (draft) → 05 (score).

"Score is 9.8. Revise."
→ Run 06 (revise) → 05 (re-score). Repeat until ≥11.0 or you decide to publish.

"This is ready."
→ Run 07 (publish). Commit output to blog repo.

"Just score this draft, don't revise."
→ Run stage 05 only.

"Research is fine but the draft doesn't work."
→ Re-run stage 04. Don't re-run 01-03. (Incremental recompilation.)

"The angle is wrong."
→ Go back to stage 01. The research may still be usable.
```
